# Claude Code adapter — hooks

Six hooks, registered in the user's `~/.claude/settings.json` (not part of this repo —
each user's is their own, generated by their client). This documents the contract; it
does not modify anyone's actual settings.

| Event | Runs | Enforces / implements |
|---|---|---|
| `SessionStart` | memory-symlink repair | keeps a per-directory memory store pointed at the single global one (a Claude Code quirk — its native memory tool is scoped by working directory) |
| `SessionStart` | `ai-atlas-resume` | surfaces a pending Atlas session handoff (`runtime/session-handoffs/latest.md`, written by `atlas tickets checkpoint`) as `additionalContext`, automatically, with no pasted prompt — see below |
| `UserPromptSubmit` | `ai-response-gate` | `internal/governance/policies/response.md` — injects the response policy when the prompt is in Arabic, so Arabic mode never depends on the model noticing core.md's routing table |
| `PreToolUse` (matcher: `Bash`) | `ai-guard-push` | `internal/governance/policies/git.yaml` — inspects every Bash command for a remote-write pattern |
| `PreToolUse` (matcher: `Write\|Edit\|MultiEdit\|NotebookEdit`) | `ai-admission-gate` | T-125's admission boundary (`REQ-AI-ADMISSION-BOUNDARY`) — see below |
| `SessionEnd` | rules/skills sync | propagates canonical rules and skills to every configured client |

## `ai-admission-gate` — T-125

Reads a `PreToolUse` payload on stdin. For `Write`/`Edit`/`MultiEdit`/`NotebookEdit` only
(every other tool, `Bash` included, is a pure no-op — this hook never inspects or blocks a
`Bash`-mediated write), it extracts the target path (`tool_input.file_path`, or
`tool_input.notebook_path` for `NotebookEdit`) and the payload's own `session_id`, then
calls `cli/atlas_admission.verify_write("claude-code", session_id, target_path)`:

  1. is there a currently **open** admission record on disk for `claude-code`/that exact
     `session_id` (never inferred, never for any other session);
  2. does that record's task/run/scope still re-verify against **live** state — run
     status, actor identity, ticket, exact scope, lease, and file claim, all checked again
     at write time via `atlas_admission.verify_admission`, never trusted from the moment
     admission was opened;
  3. does the target path resolve to **exactly** the admitted scope's own canonical path —
     never a directory expansion, never a prefix match.

Any failure at any of those three steps — including a malformed payload, a missing
`session_id`, a missing target path, or an internal error loading the library — is an
explicit `permissionDecision: deny`. Unlike `ai-guard-push` (which no-ops unless it
recognizes a specific dangerous pattern), this hook is fail-closed the other direction: it
allows exactly one proven-good case and denies everything else it is asked about.

**What is proven, and what is not:**

- `tests/test-admission-gate.py` runs the real hook as a subprocess against a disposable
  `tempfile.mkdtemp()` `ATLAS_HOME`, covering: a valid admitted write (allow); no admission
  at all; a closed admission; an admission whose underlying claim was made to expire
  between admission-open and write-time (proving the write-time check re-verifies live
  state, not a cached flag); a session with no admission of its own; a write outside the
  admitted exact scope; malformed/incomplete JSON input; and a `Read` call passing through
  untouched. This is reasoning verified against the real hook script's own stdout, not a
  mock.
- The hook is registered in the current user's `~/.claude/settings.json` through the same
  `$HOME/.claude/atlas-hook` launcher used by the other Claude hooks. Its executable bit
  is set, so the launcher can execute it directly.
- **Direct raw IDE writes and `Bash`-mediated writes remain explicitly NOT PROVEN and
  architecturally out of reach of this hook** — see T-125's own "BLOCKED BY CLIENT
  LIMITATION" notes: a raw editor write with no Atlas adapter has no code path for this
  hook to intercept, and a `Bash`-mediated file write (`echo > file`, `sed -i`, a script
  that writes) never matches the `Write|Edit|MultiEdit|NotebookEdit` tool matcher at all.

## `ai-atlas-resume` — verified, not assumed

`SessionStart` supporting `hookSpecificOutput.additionalContext` was proven, not read
about, before this hook was written: a real, isolated, headless `claude --settings
<throwaway>.json -p "<prompt with no marker in it>"` run reported back a marker that only
a `SessionStart` hook's stdout could have supplied. The same envelope shape `ai-response-gate`
already uses daily for `UserPromptSubmit` (Arabic mode activating automatically is that
mechanism, observed) was confirmed to apply to `SessionStart` too, specifically, on this
Claude Code version.

The hook itself runs `atlas context --resume --json` through the same launcher every other
hook here uses, and emits `additionalContext` only when a handoff is pending — nothing
otherwise. It is registered as its own `SessionStart` array entry (not `async`, since its
output has to be captured before the first turn), separate from the memory-symlink entry
above; the two do not interact. See `~/atlas/runtime/session-handoffs/README.md` and
`atlas context`'s own docstring (`--resume`) for the pointer format and consumption rules.

`PreToolUse` → `ai-guard-push` and `UserPromptSubmit` → `ai-response-gate` are **policy
enforcement** in the Atlas sense — deterministic implementations of a governance policy for
this client specifically, not a request that the model remember to apply one. The other two
are this adapter's own bookkeeping and aren't policies other adapters would need to
replicate identically.

`ai-response-gate` only covers the one unambiguous trigger in the response policy — the
prompt *is* Arabic script, or it is not. The fuzzier English trigger phrases ("answer",
"reply", "then me") and the "substantial report" case for English-only replies stay
model-judgement calls; core.md's routing table is the only lever for those, because there is
no reliable way to tell from the incoming prompt alone that the *reply* is about to be long,
tabular, or report-shaped. See `ai-response-gate`'s docstring for the reasoning.

## How the hooks reach the repository

Hooks run in a non-login shell with a minimal PATH and no guaranteed working directory, so
they cannot find this repository on their own. Writing its path into the hook is the wrong
fix twice over: it encodes the machine the hook was written on, and it breaks the moment
the repository moves.

Instead every hook command goes through a launcher installed once into this client's own
configuration domain:

```
$HOME/.claude/atlas-hook cli/atlas memory attach --here
$HOME/.claude/atlas-hook adapters/claude-code/ai-guard-push
$HOME/.claude/atlas-hook adapters/claude-code/ai-response-gate
```

The launcher is a **copy** of `cli/atlas-hook`, not a symlink — a symlink's target would
re-encode the repository path and break on a move, while a copy resolves at runtime and
survives one. It resolves `$ATLAS_REPO` first, `$ATLAS_REPO` as a deprecated fallback, else
`atlas_repo:`/`atlas_repo:` from
`${ATLAS_HOME:-${ATLAS_HOME:-$HOME/atlas}}/config/settings.yaml`, and `atlas init` records
that value automatically from its own location. Clone anywhere, at any depth, under any
name.

The launcher names no client. Any adapter installs the same file into its own client's
domain; nothing in it answers the question of who called it.

Moving the repository therefore never requires editing `settings.json` — re-running
`atlas init` (or updating `atlas_repo`) is enough.

Resolution failures exit 78 on stderr. `SessionStart` appends `|| true` and tolerates
that; `PreToolUse` deliberately does not, so a broken installation fails closed rather
than silently granting every push.

## Why a hook, not just a permission rule

Glob-based permission rules (e.g. `Bash(git push*)`) miss compound commands like
`cd repo && git push`. A hook that inspects the whole command string closes that gap. See
`ai-guard-push`'s own docstring for the exact matching logic.
