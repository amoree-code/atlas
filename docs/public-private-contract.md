# The Public / Private Contract

AI OS is three layers, not two. Everything else in the system rests on keeping them
apart, so the boundary is written down here and checked by `ai-os doctor`.

```
  PUBLIC — the ai-os repository
  reusable software · publishable · owns no user data
        │
        │  seeds a new workspace, once, at init.  Never reads back.
        ▼
  RUNTIME — ~/.ai
  how AI OS actually executes on this machine today
        │
        │  reads and writes your data.  Access, not ownership.
        ▼
  PRIVATE — ~/.ai-os
  memory · knowledge · projects · sessions · daily · config · skills
```

## The one idea

**Access is not ownership.**

The runtime reaches into `~/.ai-os/user/02-personal/memory` constantly — that is its job. A symlink, an
environment variable, or a hook that grants it that reach does not reclassify the data it
reaches. Memory read through `~/.claude/projects/*/memory` is still private-workspace
data, owned by you, and still may not be copied into the public repository.

Every confusion this contract prevents is a version of forgetting that sentence.

## Who owns what

| | Root | Owns |
|---|---|---|
| **Public** | the `ai-os` repo, wherever you clone it | code · CLI · adapters · policies · schemas · public skills · templates · docs · tests · examples |
| **Runtime** | `~/.ai` | hooks · runtime scripts · execution mechanisms · client integration · sync logic · transient state |
| **Private** | `$AI_OS_HOME`, default `~/.ai-os` | memory · knowledge · projects · sessions · daily records · personal config · personal skills · identity · preferences · private state |

The public repository must never contain personal memory or knowledge, project or session
history, identity, names, emails, phone numbers, credentials, private repository names,
absolute user paths, or user-specific configuration values. `ai-os privacy-scan` checks
this, and `ai-os doctor` runs it for you.

## Why the runtime layer still exists

`~/.ai` is where this system actually grew up. It holds the live hooks, the scripts, and
the client integration that work today. Folding it into the public repository is a real
architectural decision with real consequences, and V0.1.3 is not the version that makes
it.

So for now: **the runtime is an implementation detail of the V0.x migration.** It is not
moved, not deleted, not replaced, not redesigned. Tools treat it as read-only. `ai-os
doctor` reports on its health and points out where it has drifted — and stops there.

Expect this layer to change or disappear in a later version. Do not build anything that
depends on its shape.

## The invariants

`ai-os doctor` checks all four.

**Distinct roots.** No two layers share a directory, and none is nested inside another.
A nested layer looks like content of its host, which is how private data ends up staged
for a public commit.

**The private workspace is local-only.** Its git repository has no remote and never gets
one without you saying so explicitly. The public repository may have a remote. They are
never the same repository and never share history. Versioning is not publishing.

**Flow is one-directional.** Public → private happens once, at `ai-os init`, when
templates seed a new workspace. Private → public is never automatic; it requires explicit
per-item approval, and in practice means *rewriting* content generically rather than
copying it. Copying preserves the names, paths and phrasing that identify you — which is
exactly what the boundary exists to stop.

**Access is not ownership.** Restated because it is the one people lose.

## Ownership classes

Everything `ai-os init` creates falls into one of four classes. The class decides what a
future update is allowed to do to it.

| Class | Meaning | On update |
|---|---|---|
| `system-default` | seeded from a public template; AI OS's opinion of a sensible start | never overwritten; divergence is *reported*, never resolved |
| `user-owned` | written by you, or by an agent on your behalf | never touched |
| `generated` | derived and reproducible (indexes, registries) | may be regenerated by the tool that owns it |
| `runtime` | transient execution state | may be discarded freely |

The rule that matters: **an existing file is never overwritten automatically.** If a
default file exists and differs from its template, `init` says so and leaves your version
alone. It does not merge, does not back up and replace, does not ask. Deciding is yours.

## What is deliberately not built yet

Three-way template merges. Template versioning and update migration. Config schema
validation. A skill package manager. Any of these would be a system that has to be right
about your data, and the contract has to be trustworthy before anything is allowed to act
on it.
